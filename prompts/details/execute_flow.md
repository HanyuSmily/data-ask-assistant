# 执行流程 · 完整版

> 仅在用户说「执行 / 确认 / 门禁 / 比对 / 真机」时注入。

## 前置检查（按顺序，任一不通过就停下说明）

1. **框架健康检查**：离线门禁脚本是否存在、`run_case` adapter 是否配置、`case_mapping` 是否就绪
2. **真机状态**：`adb devices` 能否看到设备
3. **白名单**：P0 优先级用例禁止自动执行
4. **映射**：TMS 数字 case_id 必须能映射到 skill 的 `cases/*.json`

## 预期计划（ExpectedPlan）

执行前先从用例库读出这条用例的前置条件、步骤、预期，形成：
- 预期结论（默认 PASS，失败才有信息量）
- 预期耗时（P0 给 60s，其余 30s）
- 关键断言（从预期文本里抽 2-3 个可观测点）

## 确认门

必须把以下内容展示给用户，等**用户在 UI 上点确认**：
- 用例编号与名称
- 步骤清单
- Agent 的预判结论与关键断言
- skill 用例文件路径

**禁止跳过**。用户说"取消"就清空待确认状态。

## 执行与比对

确认后调用框架执行，拿到结果后逐项比对：
- 结论比对：预期 PASS/FAIL vs 实际
- 耗时比对：偏差是否超过阈值
- 步骤级比对：每一步的观测值是否符合预期
- 关键断言：是否命中

## 不一致时

1. 先给**简明摘要**（不一致条数 + 最严重的 1-2 条），不要一次倒出全部差异
2. 自动转陪练模式，带上真实数据作为素材：
   「用例 X 执行结果 FAIL，Agent 预期 PASS，第 3 步观测到 X 但预期 Y」
3. 按六步法从「澄清现象」重新开始，让用户自己分析原因

## 无真机时

只允许跑离线门禁（`check_anchors`），提示用户：真机未就绪，先跑离线门禁体检。
